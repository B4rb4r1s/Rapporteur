# Воркеры и очередь

`rapporteur-worker` исполняет интерфейс `Stage` из `pipeline/` и хранит задания в PostgreSQL.
Пакет конвейера не импортирует БД и веб. Доступ к материалам — через `Storage`.

## Быстрый запуск

В корне репозитория: `cp .env.example .env`, `make up`, затем `make smoke`.
Миграция очереди выполняется явно до запуска воркеров; повторить её можно `make migrate`.
У воркеров healthcheck проверяет БД, версию схемы и свежесть heartbeat процесса.
Результат dev всегда помечен `stub=true`; физические GPU в dev не запрашиваются.

Настоящие `slides` и `notes` исполняются в `make up PROFILE=gpu`.
В этом профиле подключается Ollama, требуется каталог весов и NVIDIA Container Toolkit.
Настоящий ASR пока отсутствует. LLM-этапы уже реализованы в конвейере; к реестру воркеров
они ещё не подключены. Попытка поставить неподдерживаемую задачу завершается ошибкой,
вместо неё не используется заглушка. Планировщик `Scheduler.advance(conference_id)`
готов к подключению адаптера предметной БД; сейчас его можно вызвать через CLI со снимком.

## Ручные задания

Укажите `RAPPORTEUR_INPUT` в корневом `.env`. Это каталог материалов, доступный CLI
только для чтения как `/input`; по умолчанию используется `data/` в корне репозитория.

```bash
docker compose --env-file .env -f deploy/compose.yaml --profile dev run --rm cli enqueue notes /input/заметки.txt
docker compose --env-file .env -f deploy/compose.yaml --profile dev run --rm cli enqueue slides /input/доклад.pptx --priority 100
docker compose --env-file .env -f deploy/compose.yaml --profile dev run --rm cli enqueue asr /input/запись.wav
```

Команда возвращает UUID задания. `show <UUID>` показывает состояние и ссылку на результат,
`cancel <UUID>` отменяет задание. Повторная постановка того же этапа с тем же входом,
режимом, версией и конфигурацией возвращает тот же UUID, включая завершённую или отменённую
задачу. Для намеренно нового результата нужны изменённый вход, конфигурация или версия.

Для GPU добавьте `-f deploy/compose.gpu.yaml` и замените `--profile dev` на `--profile gpu`
во всех командах. Dev-воркер не забирает GPU-задания, GPU-воркер не забирает dev-задания.
В CLI `--mode` означает режим развёртывания, `--resource` — роль исполнителя;
в dev роль `gpu` тоже работает без физических GPU.

Это ручной запуск отдельного этапа, как `rapporteur run`: он не создаёт конференцию и
не подменяет проверки человека в планировщике графа. Идентификаторы конференции и доклада
в таких заданиях пусты. Тексты материалов, имена исходных файлов, пароли и DSN не пишутся
в обычные логи воркера.

## Планирование графа

`Scheduler` принимает функцию `load_state(conference_id)`, возвращающую согласованный снимок
`ConferenceState`: файлы с их видами и ссылками Storage, доклады с привязками и статусами,
подтверждённые проверки и конфигурации этапов. Предметными таблицами по-прежнему владеет
будущий backend. Снимок — внутренний формат адаптера, он не заменяет `conference.yaml`.

`preview` вычисляет готовые задания и причины ожидания без записи в очередь. `advance`
ставит готовые задания; повторные и конкурентные вызовы не создают дубликатов. Перед
запуском зависимости проверяются в области текущего доклада или всей конференции согласно
ADR-009. Доклады draft/not_held/insufficient_data не обрабатываются. Отсутствующие виды файлов
не блокируют зависимые этапы. Без записей проверка границ пройдена автоматически, подтверждение
привязки остаётся обязательным. В GPU-режиме результат заглушки отвергается.

Версия обработчика, конфигурация и хэши входов участвуют в ключе задания. Ошибка файла
с кодом `FailureCode` завершает файловую зависимость; ошибка инфраструктуры или отмена
оставляет зависимые этапы заблокированными. Артефакты докладов не смешиваются: зависимость
от этапа доклада выбирает только тот же доклад, от файлового этапа — его привязанные файлы.

Пример только для dev: `workers/examples/dev-state.json` содержит вымышленные UUID и хэш,
исходный файл не нужен, заглушки его не разбирают. После `make up`:

```bash
mkdir -p data
cp workers/examples/dev-state.json data/
docker compose --env-file .env -f deploy/compose.yaml --profile dev run --rm cli plan /input/dev-state.json
docker compose --env-file .env -f deploy/compose.yaml --profile dev run --rm cli advance /input/dev-state.json
```

Первый `advance` ставит inventory. После завершения задания повторите команду — она
поставит notes. Дальше plan покажет ожидание подтверждения привязки; если его добавить
в `gates`, следующий блокер — отсутствие реализации facts. Повторы после готового этапа
не создают новых заданий. Состояние задания можно смотреть командой `show <UUID>`.

Автоматические вызовы после завершения этапа, изменения привязок и подтверждения проверок
подключаются при реализации backend. Адаптер должен обеспечивать согласованность снимка
с изменениями предметных данных и проверок; CLI не ведёт собственный реестр конференций.

## Надёжность

- Захват через `FOR UPDATE SKIP LOCKED`: два воркера не получают одну попытку.
- Приоритет важнее группировки по последнему этапу. Группировка по профилю модели появится
  вместе с LLM-этапами.
- У попытки свой UUID и lease, по умолчанию 60 секунд; heartbeat продлевает его раз в 20 секунд.
  Истёкший lease нельзя возобновить; reaper возвращает задачу на повтор с backoff и jitter.
- По умолчанию первый запуск и до трёх повторов. Невалидный вход не повторяется.
- Отмена работающей задачи запрещает публикацию результата, даже если обработчик завершился.
- Обработчик пишет во временный каталог. Публикация выполняется под блокировкой строки
  задания после проверки владельца и срока lease; старая попытка не может перезаписать новую.
- При сбое публикации транзакция задания откатывается. На томе могут остаться файлы,
  на которые нет ссылки успешной задачи; повтор выполняет публикацию заново.
- Публикация общего ключа кэша сериализована advisory-блокировкой. Если два задания
  вычислили один результат, второе использует уже опубликованный артефакт; его produced_at
  и SHA-256 остаются прежними, ссылки первой конференции сохраняют целостность.

Схема `rapporteur_queue` и её версия принадлежат этому пакету. Команда миграции
сериализуется advisory-блокировкой. Backend имеет собственные миграции Alembic
для предметных таблиц; общая цель make migrate запускает оба шага.

## Проверки

`make -C workers check` запускает Ruff, mypy и pytest в контейнерах. Для тестов поднимается
отдельный PostgreSQL без дискового тома и опубликованного порта, после тестов он удаляется.
Каждый интеграционный тест создаёт отдельную БД с префиксом `rapporteur_test_` и удаляет
только её. Если запускаете pytest локально, нужен `TEST_DATABASE_URL` на тестовый сервер
с правом создания БД; без него интеграционные проверки помечаются skipped.

Основные сценарии: конкуренция, блокированная строка, истёкший lease, отмена во время
обработки, публикация старой попыткой, ограниченные повторы, медленный этап с heartbeat,
изоляция dev/gpu, настоящие заметки и сквозной smoke через оба воркера. Для планировщика
проверяются области зависимостей, проверки человека, ошибки файлов, смена версии и
конфигурации, конкурентный advance, CLI и сохранение SHA общего кэша.
