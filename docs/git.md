# Работа с git

Короткие правила, чтобы история оставалась одной линией вокруг `main`.

## Одна основная ветка

- Основная ветка — `main`. На GitHub она же стоит веткой по умолчанию (Settings → General → Default branch).
- В `main` попадает только то, что прошло `make check` (README, «Перед слиянием в main»).
- PR всегда открывается **в** `main`, никогда **из** `main` в другую ветку. Если GitHub предлагает базой не `main`, нужно исправить базу в PR, а не сливать.

## Ветка на задачу

- Новая работа начинается со свежего `main`:

  ```bash
  git switch main
  git pull --ff-only
  git switch -c feat/p1-15-short-name
  ```

- Имя: `тип/задача-суть`. Типы те же, что в сообщениях коммитов: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`. Номер задачи из backlog.md, если он есть.
- Одна ветка — одна задача. Ветка живёт дни, а не недели. Если задача большая, лучше разбить её на несколько PR.
- Ветки от Codex и других агентов подчиняются тем же правилам: от свежего `main`, PR в `main`, удалить после слияния.

## Коммиты

- Формат: `тип(область): что сделано (номер задачи)`, по-русски, как в истории. Пример: `feat(report): сборка справки по выборке (P1-11)`.
- Коммит — одно законченное изменение. Статус задачи в backlog.md меняется в том же PR, что и код.
- В git не попадают `data/`, `docs/SoW/`, `.env`, кэши и сборки. Перед коммитом стоит посмотреть `git status`.

## Перед PR

- Подтянуть `main` и проверить, что ветка на нём:

  ```bash
  git fetch Rapporteur
  git rebase Rapporteur/main
  ```

  Rebase делается только для своей ветки, которую ещё никто не взял. Если ветку уже кто-то использует, вместо rebase — `git merge Rapporteur/main`.
- Запустить `make check`, результат записать в описание PR.

## После слияния

- Удалить ветку на GitHub (кнопка в PR; лучше включить Settings → General → «Automatically delete head branches»).
- Удалить ветку локально и почистить ссылки на удалённые ветки:

  ```bash
  git switch main
  git pull --ff-only
  git branch -d feat/p1-15-short-name
  git fetch --prune
  ```

- `git branch -d` откажется удалять невлитую ветку. Это защита: `-D` используется только когда точно известно, что работа не нужна.

## Чего не делать

- Не коммитить прямо в `main` и не пушить в него без PR.
- Не сливать `main` в рабочие ветки ради «синхронизации» через PR — для этого `rebase` или `merge` локально.
- Не держать вторую «основную» ветку. Если ветка по умолчанию на GitHub не `main`, это первое, что нужно исправить.
- Не делать `git push --force` в `main`. В свою ветку — только `--force-with-lease` и только после rebase.

## Проверка порядка

Раз в неделю или перед релизом:

```bash
git fetch --prune
git branch -vv
git branch --merged main
```

Всё из `--merged main`, кроме самой `main`, можно удалить.
