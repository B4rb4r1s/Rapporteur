# ADR-014. Упрощение: один пакет, один compose, обработка в процессе приложения

- Статус: Принято командой 1; ждёт просмотра командой 2
- Дата: 2026-11-09
- Ведёт: К1 · лид
- Связано: spec §3, §6, §8, §11, §14, ADR-001, ADR-004, ADR-005, ADR-007, ADR-009, ADR-011, ADR-012, ADR-013

## Контекст

К концу Ф1 в репозитории было пять отдельных пакетов: contracts, pipeline, workers, backend
и frontend. У каждого были свои Dockerfile, compose.yaml, Makefile и lock-файл: всего восемь
compose-файлов и шесть Dockerfile. В основном compose работали десять сервисов: web, db,
init-data, worker-cpu, worker-gpu, scheduler, migrate, backend-migrate, cli и ollama.
Около половины кода обслуживало инфраструктуру, а не справку:

- своя очередь на PostgreSQL с lease и heartbeat (ADR-004);
- граф этапов в YAML с планировщиком (ADR-009);
- обёртки этапов со ссылками на артефакты и снимками конференции;
- режимы dev и gpu с заглушками этапов;
- перенос результатов задач в предметную БД (ADR-013);
- ETag и If-Match на каждом объекте (ADR-012);
- генерация JSON Schema и TS-типов, которые фронтенд не использовал;
- вторая дорога к справке через CLI в обход приложения.

Справку при этом обслуживает одна GPU через Ollama, а Ollama и так выполняет запросы
по очереди. В конференции до ста докладов, пользуются приложением несколько человек
в локальной сети. Сложность мешала разработке больше, чем помогала.

## Варианты

1. Оставить архитектуру, сократить только compose и Makefile.
2. Отдельный процесс-воркер, который берёт доклады из БД по статусу, без очереди и графа.
3. Обработка в фоновом потоке приложения, база SQLite, один образ и один compose.

## Решение

Вариант 3. Его выбрал лид проекта на обсуждении 2026-11-09.

**Один пакет.** Весь Python-код — пакет `rapporteur` в `src/` с одним `pyproject.toml`
и одним `uv.lock`. Контракты стали модулем `rapporteur.contracts`: Pydantic-модели
и их правила остались, генерация JSON Schema, TS-типов и примеров удалена. JSON Schema
ответов LLM по-прежнему строится из моделей `*Draft` при запросе к модели.

**Этапы — функции.** `parse_slides`, `parse_notes`, `build_pack`, `extract_facts`,
`verify_facts`, `write_summary` и `build_report` принимают данные и возвращают результат.
Интерфейс `Stage`, `StageInputs`, `StageOutput`, `ArtifactRef`, `ArtifactMeta`
и реестр этапов удалены (изменение ADR-007 в части интерфейса этапа).

**Обработка.** Доклад ставится в очередь полем `talks.job = 'queued'`. Это происходит при
запуске обработки, при подтверждении привязок после запуска и при повторе. Один фоновый
поток приложения берёт доклады по одному и проходит цепочку spec §6: разбор → пакет →
факты → сверка → сводка. Затем он записывает версию сводки и переводит доклад в `processed`.
После перезапуска прерванные доклады обрабатываются заново. Очередь ADR-004 и граф ADR-009
удалены. Порядок шагов задан кодом `rapporteur/processing.py`. Проверка привязок работает так:
обрабатываются только доклады с подтверждёнными файлами.

**Кэш шагов** (уточнение ADR-005). Результаты разбора и LLM-шагов лежат на томе
в `cache/<шаг>/<ключ>.json`. Ключ — хэш версии шага, входа и конфигурации, включая профиль
модели. Повтор после сбоя или та же перепривязка не обращаются к модели заново. Повторный
результат из кэша не создаёт новую версию сводки.

**База.** SQLite в томе данных (`/data/rapporteur.db`) вместо PostgreSQL. Схема создаётся
при старте приложения, истории миграций нет. При несовместимом изменении схемы dev-данные
загружаются заново. Установка с данными получит миграцию вместе с таким изменением.
Пользователь `local`, поля `owner_id`, `edited_by` и `version` у объектов удалены
(изменение ADR-011). Автор версии сводки — признак `human_edit`.

**API** (изменение ADR-012). ETag и If-Match удалены. Правка и проверка сводки передают
номер версии в теле запроса, устаревшая версия даёт 409. Ошибка — `{"message": ...}`.
Справка собирается прямо в запросе за секунды и сразу возвращает версию. Сущность «справка»
с выборкой упразднена: есть версии справки конференции. Задачи `/jobs` заменены ходом
обработки докладов и повтором `/talks/{id}/retry`.

**Без режима dev.** Обработка всегда идёт через Ollama. Заглушки модели остались только
в тестах (`ScriptedClient`). Установка без NVIDIA GPU не поддерживается.

**Развёртывание.** Один `Dockerfile` с этапами `web` (сборка React), `app` (приложение)
и `dev`/`web-deps` (проверки). Один `compose.yaml` с сервисами `app` и `ollama`; служебные
`pull`, `dev`, `web-dev` вынесены в профиль `tools`. Один `Makefile`: `up`, `down`, `check`,
`lock`, `pull`. Сети: `internal` без выхода наружу и `edge` без NAT для порта, как раньше.

**Что сохранено.** Заготовки аудио и видео: контракты стенограммы и сегментов, локатор
по времени, приём записей с длительностью, место записей в пакете. Доклад, у которого
есть только запись, получает ошибку `no_sources` с пометкой «распознавание записей
появится в Ф2». Процесс двух команд (ADR-007, ADR-011) тоже сохранён, CODEOWNERS
переведён на новые каталоги.

**Что удалено.** CLI `rapporteur run` и `make report`: справка собирается только через
приложение. Замер привязок `benchmark-bindings` и smoke-скрипт Ollama: результаты остались
в `docs/benchmarks/`.

## Последствия

- Около 6 тыс. строк кода и тестов меньше. Сервисов при работе два, а не десять.
  `make check` идёт в двух контейнерах без PostgreSQL.
- Граница команд проходит по модулям пакета, а не по пакетам: `rapporteur/contracts/`,
  `ingest/`, `summarize/`, `report/` — ядро; `app.py`, `db.py`, `materials.py`,
  `processing.py`, `frontend/` — платформа.
- Обработка идёт строго по одному докладу. Параллельные запросы к двум GPU (ADR-002)
  потребуют пула потоков или второго процесса. Если очередь в БД переживёт этот переход,
  отдельный сервис-воркер можно вернуть без изменения API.
- Несколько процессов uvicorn запускать нельзя: каждый стартует свой поток обработки.
- Текущие dev-данные из томов PostgreSQL не переносятся.

## Когда пересмотреть

- Замеры на A100 (P0-03, P1-10) покажут, что параллельная обработка докладов на двух
  GPU заметно сокращает время конференции.
- Одновременно работает столько пользователей, что SQLite с одной записью за раз
  становится узким местом.
- Появятся задачи, которым нужна отмена, приоритеты или зависимости между этапами шире
  одного доклада (разбиение записей Ф3).
