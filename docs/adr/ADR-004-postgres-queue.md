# ADR-004. Очередь задач на PostgreSQL

- Статус: Принято; выбор между своей реализацией и procrastinate делается в P1-02
- Дата: 2026-10-27
- Ведёт: К2 · A
- Связано: spec §7.2, §8.2, ADR-002

## Контекст

- Один сервер, один GPU-воркер и несколько CPU-воркеров; задач десятки в минуту, не тысячи.
- Задачи длинные (распознавание многочасовых записей) и короткие интерактивные (перегенерация одной сводки).
- Задачи переживают перезапуск, есть повторы и отмена; результат не публикуется дважды.
- ТЗ команды 2 предлагало Redis и Celery с outbox, lease и сервисом сверки; ТЗ команды 1 допускало очередь на PostgreSQL.

## Варианты

1. Redis + Celery + outbox-диспетчер + сверка по БД.
2. Таблица задач в PostgreSQL, захват через `SELECT … FOR UPDATE SKIP LOCKED`, своя реализация.
3. Готовая библиотека очереди на PostgreSQL (procrastinate).

## Решение

Очередь на PostgreSQL (вариант 2 или 3). Между своей реализацией и procrastinate выбираем в P1-02 по короткому прототипу и записываем выбор сюда.

Обязательные свойства:

- статусы `queued`, `running`, `succeeded`, `failed`, `cancelled`, `retry_wait`, `cancel_requested`;
- приоритеты: интерактивные задачи раньше пакетных; задачи одного этапа и профиля модели группируются (ADR-002);
- lease и heartbeat: задача без heartbeat сверх лимита возвращается в очередь; результат записывается, только если lease ещё действителен, поэтому старый воркер не перезаписывает результат новой попытки;
- повторы с backoff и jitter для временных ошибок, по умолчанию до трёх; невалидный вход не повторяется; нехватка памяти GPU становится контролируемой ошибкой с диагностикой, а не бесконечным повтором;
- отмена проверяется между шагами; уже идущий вызов модели может завершиться, но результат отменённой задачи не публикуется;
- длинные задачи режутся на шаги (распознавание кусками около 10 минут), чтобы интерактивные задачи не ждали часами;
- идемпотентность через ключ кэша этапа (ADR-005).

## Последствия

- Нет Redis, брокера и outbox-диспетчера: задача создаётся в той же транзакции, что и данные.
- Состояние очереди видно обычным SQL; страница состояния показывает глубину и возраст очереди.
- Тесты: падение воркера, истёкший lease, повторная доставка, отмена во время шага, короткая задача обгоняет длинную.

## Когда пересмотреть

- Воркеры переезжают на несколько серверов.
- Нагрузка на очередь начинает заметно влиять на PostgreSQL.
