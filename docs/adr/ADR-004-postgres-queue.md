# ADR-004. Очередь задач на PostgreSQL

- Статус: Принято; своя реализация очереди, исполнитель графа в P1-02 ещё в работе
- Дата: 2026-10-27
- Ведёт: К2 · A
- Связано: spec §7.2, §8.2, ADR-002

## Контекст

- Один сервер, один GPU-воркер и несколько CPU-воркеров; задач десятки в минуту, не тысячи.
- Задачи длинные (распознавание многочасовых записей) и короткие интерактивные (перегенерация одной сводки).
- Задачи переживают перезапуск, есть повторы и отмена; результат не публикуется дважды.
- ТЗ команды 2 предлагало Redis и Celery с outbox, lease и сервисом сверки; ТЗ команды 1 допускало очередь на PostgreSQL.

## Варианты

1. Redis + Celery + outbox-диспетчер + сверка по БД.
2. Таблица задач в PostgreSQL, захват через `SELECT … FOR UPDATE SKIP LOCKED`, своя реализация.
3. Готовая библиотека очереди на PostgreSQL (procrastinate).

## Решение

Вариант 2: небольшая собственная очередь на Psycopg 3. Прототип в `workers/` проверен
интеграционными тестами на PostgreSQL 17.11: `SKIP LOCKED`, lease и heartbeat, отмена,
приоритет, повторы и запрет публикации старой попыткой. Здесь не нужны брокер и
отдельная модель задач библиотеки procrastinate; контроль владения и публикации остаётся
в одном небольшом модуле. Планировщик `Scheduler.advance(conference_id)` работает поверх
очереди со снимком конференции; интеграция с предметной БД остаётся в P1-04.

Схема `rapporteur_queue` принадлежит `workers/`: команда `rapporteur-worker migrate`
применяет начальную SQL-миграцию под транзакционной advisory-блокировкой. Повторный запуск
ничего не меняет, неизвестная версия отвергается. Будущие миграции Alembic в `backend/`
владеют предметными таблицами и пользователем `local`, а не таблицами очереди. Это позволяет
запускать воркеры до реализации P1-04 без зависимости конвейера от веба или БД.

Обработчик пишет в отдельный временный каталог попытки. Публикация начинается только после
захвата строки задания и повторной проверки lease; отмена, завершение и возврат в очередь
сериализованы этой строкой. Транзакция хранит ссылку на результат. Файловая система тома
не транзакционна: при сбое записи могут остаться файлы без успешной задачи; они не считаются
готовым результатом очереди и перезаписываются при повторе.

У разных заданий может быть общий ключ кэша. Публикация также получает транзакционную
advisory-блокировку этого ключа и повторно проверяет кэш. Второй вычислитель использует
первый готовый артефакт, сохраняя его время создания и SHA-256. Так отдельные задания
конференций не ломают ранее сохранённые ссылки на общий результат. Lease повторно
проверяется после ожидания обеих блокировок.

Dev- и GPU-задания разделены полем `mode`, версии заглушек участвуют в ключе кэша.
По умолчанию допускаются четыре попытки (первый запуск и три повтора). Пока обработчики
LLM отсутствуют, группировка реализована по этапу; группировка по профилю модели добавится
вместе с LLM-обработчиками. Приоритет всегда важнее группировки.

Обязательные свойства:

- статусы `queued`, `running`, `succeeded`, `failed`, `cancelled`, `retry_wait`, `cancel_requested`;
- приоритеты: интерактивные задачи раньше пакетных; задачи одного этапа и профиля модели группируются (ADR-002);
- lease и heartbeat: задача без heartbeat сверх лимита возвращается в очередь; результат записывается, только если lease ещё действителен, поэтому старый воркер не перезаписывает результат новой попытки;
- повторы с backoff и jitter для временных ошибок, по умолчанию до трёх; невалидный вход не повторяется; нехватка памяти GPU становится контролируемой ошибкой с диагностикой, а не бесконечным повтором;
- отмена проверяется между шагами; уже идущий вызов модели может завершиться, но результат отменённой задачи не публикуется;
- длинные задачи режутся на шаги (распознавание кусками около 10 минут), чтобы интерактивные задачи не ждали часами;
- идемпотентность через ключ кэша этапа (ADR-005).

## Последствия

- Нет Redis, брокера и outbox-диспетчера: задача создаётся в той же транзакции, что и данные.
- Состояние очереди видно обычным SQL; страница состояния показывает глубину и возраст очереди.
- Тесты: падение воркера, истёкший lease, повторная доставка, отмена во время шага, короткая задача обгоняет длинную.

## Когда пересмотреть

- Воркеры переезжают на несколько серверов.
- Нагрузка на очередь начинает заметно влиять на PostgreSQL.
