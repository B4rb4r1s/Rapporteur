# ADR-012. Предметная БД и HTTP API MVP

- Статус: Принято командой 2; ждёт просмотра командой 1; частично заменено ADR-014: SQLite вместо PostgreSQL, без ETag/If-Match
- Дата: 2026-11-04
- Ведёт: К2 · B
- Связано: spec §7, §11, P1-04, ADR-001, ADR-004, ADR-006, ADR-011

## Контекст

Спецификация определяет группы API и формат ошибок, но не маршруты и передачу версии
изменяемого объекта. Контракты Conference, Talk и Report содержат version, Section и
Person — нет. Схема очереди принадлежит workers, её миграция уже отделена от предметной БД.

## Решение

- Предметная БД — PostgreSQL; доступ через SQLAlchemy Core 2.0, миграции Alembic.
  Начальная миграция хранит собственный SQL-снимок схемы, не импортирует изменяемые
  определения таблиц приложения и создаёт пользователя local с постоянным UUID.
- Миграция запускается отдельной командой `rapporteur-backend migrate` и сериализуется
  advisory-блокировкой. Web не применяет миграции при старте.
- CRUD реализован для конференций, секций, персон, докладов и конфигураций справок.
  Создание вложенного ресурса и его список находятся под родителем; чтение, PUT и DELETE
  конкретного объекта — по собственному UUID. Полный перечень — в `docs/api.md`.
- Все изменяемые предметные объекты имеют внутреннюю версию и ETag вида `"1"`.
  PUT и DELETE требуют сильный If-Match. Сравнение под блокировкой строки, изменение
  данных и увеличение версии выполняются в одной транзакции; устаревшая версия — 409.
  Публичные модели Section и Person не меняются: их версия доступна в заголовке.
- owner_id, author_id и внутренний edited_by назначаются сервером от local; входные
  модели запрещают лишние и служебные поля. Учётных записей и проверки прав в MVP нет.
- Выборка справки проверяется на принадлежность конференции, выбранным секциям и дням.
  Ссылки на выбранные доклады и секции защищены FK. Удалить используемый объект отдельно
  нельзя; удаление всей конференции каскадно удаляет её предметные записи. Файлы на томе
  эта операция не удаляет.
- Изменения коммитятся до отправки HTTP-ответа, включая отложенные проверки FK.
- История ReportVersion хранится отдельно; API читает версии, а запись результатов сборки
  подключается вместе с обработчиком экспорта. Публичного ввода произвольного текста справки нет.
- API задач читает существующую очередь и атомарно меняет допустимые состояния. Повтор
  после failed/cancelled использует тот же UUID задания, обнуляет счётчик попыток и сбрасывает
  lease/token: старая попытка не получает права публикации. Повтор уже ожидающей/работающей
  задачи отклоняется с 409. Приоритет меняется только у ожидающей задачи.
- Ошибки API, валидации, отсутствующих маршрутов и БД имеют ApiError и X-Request-ID.
  SQL, параметры подключения и тексты исключений не возвращаются пользователю.
- OpenAPI сохраняется в `backend/openapi.json` и доступен на `/openapi.json`.
  Swagger/ReDoc с внешними CDN отключены. `/health` — liveness, `/ready` проверяет БД
  и совместимость применённой миграции.

## Последствия

Контракты данных не меняются. Веб работает до интеграции загрузки и обработки, а список
маршрутов и правила версий определены для frontend. Backend не владеет схемой очереди
и не импортирует реализации этапов. Интеграция снимка планировщика, подтверждений человека,
загрузки файлов и редактора сводок продолжается в P1-05 и P1-12.
