# ADR-002. Модель и режим работы двух GPU

- Статус: Предложено; решение по замерам P0-03 и P1-10
- Дата: 2026-10-27
- Ведёт: К1 · лид, замеры К2 · A
- Связано: spec §8.2, §9, §12, ADR-004

## Контекст

- Сервер: 2× A100 40 ГБ, карты связаны NVLink, оперативной памяти больше 200 ГБ. Аппаратного FP8 нет.
- Точность важнее скорости, но пользователей много: правка одной сводки не должна ждать многочасового распознавания чужой конференции.
- На GPU работают LLM (поиск объявлений, коррекция терминов, факты, сводки, критик), VLM для слайдов, ASR и эмбеддинги.
- NVLink делает tensor parallel на двух картах дешёвым. Большая RAM позволяет усыплять модель в sleep mode vLLM и будить её, по оценке, за секунды вместо минут полной загрузки.

## Варианты

### Режимы

| | A. Раздельный | B. Монопольный | C. Совместный |
| --- | --- | --- | --- |
| LLM | ~27B в FP8 (W8A16) или 4 битах на одной карте | ~27B в BF16 или MoE на двух картах | ~27B в BF16 на двух картах, около 85% памяти |
| Речь | вторая карта целиком | обе карты по очереди с LLM | остаток памяти обеих карт |
| KV-кэш, оценка | ≈ 8 ГБ при FP8, ≈ 20 ГБ при 4 битах | ≈ 8–10 ГБ на карту | ≈ 4–6 ГБ на карту |
| Смена моделей | не нужна | на каждой смене этапа | не нужна |
| Главный риск | квантование снижает точность | очередь ждёт смены этапа | нехватка памяти на пиках и длинных докладах |

### Модели-кандидаты

| Кандидат | Веса | Роль |
| --- | --- | --- |
| Qwen3.6-27B, BF16 | ≈ 54 ГБ | базовый профиль |
| Qwen3.6-35B-A3B, BF16 | ≈ 70 ГБ | быстрый профиль: поиск объявлений, коррекция терминов |
| MoE ~120B-A10B в 4 битах, например Qwen3.5-122B-A10B | ≈ 65–70 ГБ | кандидат на качество фактов и сводок |
| MoE 200B+ в 4 битах | ≈ 120–130 ГБ | не помещается в VRAM; только эксперимент с экспертами в RAM |

## Решение (предлагаемое)

1. worker-gpu поддерживает все три режима; режим задаётся конфигурацией, а не кодом.
2. Кандидат по умолчанию — режим C с ~27B в BF16, если KV-кэша хватает на доклад в 32K токенов при нужной параллельности. Иначе режим B со sleep mode. Режим A — если на эталоне 4-битная или FP8-версия не хуже BF16.
3. Профили назначаются по этапам: быстрая MoE может искать объявления по многочасовым стенограммам, сильная модель — писать факты и сводки. Несколько моделей одновременно держатся в sleep mode в RAM.
4. Управление vLLM (запуск профиля, sleep, wake) идёт через управляющий процесс внутри контейнера `vllm` по HTTP. Доступа к Docker socket нет.
5. Модель выбирается по метрикам §12 на эталоне в таком порядке: ноль выдумок, доля подтверждённых утверждений, полнота, стиль, затем время обработки конференции на 100 докладов.

## План замеров

- P0-03: время загрузки, sleep и wake для 27B в BF16 на двух картах; VRAM и KV-кэш при 32K; токены в секунду на 1 и 8 параллельных запросах; память и скорость трёх ASR-движков.
- P1-10: качество трёх кандидатов LLM на эталоне через `make eval`; совместный режим под нагрузкой ASR; время на конференцию, экстраполированное с замера.

## Последствия

- Планировщик (ADR-004) учитывает этап и профиль модели и группирует задачи, чтобы смен было мало.
- Профиль модели хранит ревизию весов; офлайн-комплект включает веса всех разрешённых профилей.
- До принятия решения разработка идёт на заглушках и на базовом профиле.

## Когда пересмотреть

- Выходит модель, заметно лучшая на эталоне.
- Нагрузка пользователей превышает пропускную способность выбранного режима.
- Замеры sleep и wake оказываются на порядок хуже оценки.
