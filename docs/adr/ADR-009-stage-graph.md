# ADR-009. Граф этапов и ожидание проверок

- Статус: Принято; команда 2 согласна 2026-11-03
- Дата: 2026-11-01
- Ведёт: К1 · лид
- Связано: spec §3 (п. 5, 7), §4.2, §6, §8.2, §14, ADR-004, ADR-007

## Контекст

`Stage` из ADR-007 описывает один запуск этапа. Нигде не записано, кто решает, какой этап идёт следующим, как конвейер ждёт проверок человека (привязка материалов, границы докладов) и как обработка расходится с конференции на доклады. Порядок этапов — предметное знание команды 1, очередь и исполнение — зона команды 2, поэтому задача выпала из обоих потоков и из бэклога.

## Варианты

1. Порядок зашит в воркерах. Просто, но каждое изменение конвейера требует правок команды 2, а CLI и `make eval` повторяют ту же логику.
2. Каждый этап сам ставит следующие. Логика размазана по этапам, а этапы по ADR-007 не знают про очередь.
3. Декларативный граф: команда 1 описывает этапы и зависимости данными, воркеры его исполняют.

## Решение

Вариант 3.

- Граф лежит в `pipeline/graph.yaml` и проверяется моделью `PipelineGraph` из `contracts/`. Для каждого этапа заданы область (`conference`, `file`, `talk`), ресурс (`cpu`, `gpu`), зависимости и проверки человека, которые должны быть пройдены.
- Функция `advance(conference_id)` в `workers/` идемпотентна: сравнивает граф с состоянием и ставит задачи для этапов, у которых готовы зависимости и пройдены проверки. Её вызывают завершение задачи и подтверждение человека.
- Этап с областью `talk` разворачивается в одну задачу на доклад, поэтому изоляция докладов (принцип 1) следует из графа.
- Ожидание человека — это отсутствие задачи, а не её статус. Новый статус в ADR-004 не нужен, очередь не держит заблокированных записей.
- CLI `rapporteur run` и `make eval` используют тот же граф.

Проверки в графе: `binding_confirmed` и `boundaries_confirmed`. Проверка сводок не блокирует граф: она действует при сборке справки, которая запускается по запросу пользователя (spec §4.2).

## Последствия

- Порядок этапов меняется правкой данных в зоне К1, код воркеров при этом не трогается.
- В бэклог добавляется P0-08. Контракт `PipelineGraph` входит в P0-01, `advance` — в P1-02.
- Планировщик группировки по профилю модели (ADR-002) работает поверх уже поставленных задач и от графа не зависит.

## Когда пересмотреть

- Появятся этапы с условным ветвлением, которое не выражается зависимостями и проверками.

## Семантика графа

Уточнение от 2026-11-03, сделано в P0-08 по ADR-011 командой 1 и ждёт просмотра командой 2. Решение ADR не меняется; здесь правила, без которых `advance` пришлось бы додумывать в коде.

**Входные файлы.** У этапа есть `file_kinds` (contracts 0.2.0). Этап с областью `file` запускается на каждый файл этих видов. Этап конференции с непустым списком нужен, только если такие файлы есть. У этапа доклада списка нет.

**Зависимости.**

1. Этап доклада ждёт этапы того же доклада, этапы конференции и этапы с областью `file` по файлам этого доклада. Для записи это файлы, отрезки которых отнесены к докладу.
2. Этап с областью `file` ждёт этапы конференции. Зависимостей между этапами `file` в графе нет.
3. Этап конференции ждёт все файлы конференции подходящих видов.
4. Этап без входов (в конференции нет файлов его видов) задач не создаёт и считается выполненным, поэтому зависящие от него этапы не ждут.
5. Ошибка файла (`FileFailure`) завершает этап для этого файла: зависящие этапы идут дальше, а файл показывается пользователю с ошибкой (spec §6).

**Проверки человека.** `binding_confirmed` — пользователь подтвердил привязку материалов к докладам (проверка 1). `boundaries_confirmed` — пользователь подтвердил границы в записях (проверка 2); если записей в конференции нет, проверка считается пройденной.

**Этапы без реализации.** Заглушка этапа запускается только в профиле `dev`. В профиле `gpu` `advance` не ставит задачу этапу без настоящей реализации, и зависящие этапы ждут, кроме случая из правила 4. Так результат заглушки не попадает в настоящую справку (spec §17). Сейчас без реализации `asr` и `segment` (Ф2–Ф3), а в Ф1 записей нет, поэтому оба этапа без входов.

**Проверки сверх модели.** `pipeline/src/rapporteur_pipeline/graph.py` дополнительно требует: выход этапа — артефакт из `contracts/`; этап с LLM работает на `gpu`; этапы шага сводки (`FactsArtifact`, `VerifiedClaimsArtifact`, `SummaryArtifact`) имеют область `talk`. Команда `rapporteur graph` проверяет граф и печатает допустимый порядок исполнения.

## Текущий планировщик

`workers/src/rapporteur_workers/scheduler.py` реализует чистую функцию `plan` и
`Scheduler.advance(conference_id)`. Адаптер `load_state` поставляет согласованный снимок
файлов, привязок, статусов докладов и проверок; результаты этапов читаются из очереди.
Доклады `draft`, `not_held` и `insufficient_data` не разворачиваются в задачи.
Файловая зависимость считается завершённой после успешного результата или ошибки
файла с кодом `FailureCode`; ошибка инфраструктуры и отмена не пропускают зависимые этапы.

Задания имеют ключ с областью, идентификатором цели и конференции, режимом, версией
обработчика и хэшами входов и конфигурации. Ограничение уникальности очереди защищает
повторные и конкурентные вызовы. Готовый результат с неподходящей метаинформацией не
используется. Для этапов без зависимостей источники также ограничиваются областью
доклада и `file_kinds`, чтобы отсутствие needs не расширяло контекст до конференции.

CLI-команды `plan` и `advance` принимают внутренний JSON-снимок. Собственный реестр
конференций планировщик не хранит. Адаптер БД и автоматические вызовы после завершения
задачи и подтверждения человеком подключаются вместе с backend; при изменении данных
адаптер обеспечивает согласованность снимка и проверок. Текущая интеграция не заменяет
подготовку `TalkFragmentPack` и разметку фрагментов для будущих обработчиков facts.
