# ADR-007. Граница между командами

- Статус: Принято
- Дата: 2026-10-27
- Ведёт: К1 · лид
- Связано: spec §8.4, §14, ADR-003, [CODEOWNERS](../../CODEOWNERS)

## Контекст

- Над проектом работают две команды. Команда 1 ведёт проект и отвечает за ядро: контракты, оценку, разбиение записей, сводки, сборку справки. Команда 2 строит платформу: инфраструктуру, GPU, приём файлов, речь, веб-приложение.
- Команды должны работать параллельно с первой недели и не блокировать друг друга.
- Ошибка на границе (несовпадение форматов артефактов) обнаруживается поздно и стоит дорого.

## Варианты

1. Общая кодовая база без явной границы, договорённости в чате.
2. Граница по контрактам данных и интерфейсу этапов, закреплённая в коде и в CODEOWNERS.

## Решение

Вариант 2.

**Контракты.** Пакет `contracts/` — Pydantic-модели всех артефактов и сущностей, сгенерированные из них JSON Schema и TypeScript-типы для фронтенда, примеры в `contracts/examples/`. Версия пакета по semver в `contracts/VERSION`; несовместимое изменение повышает старшую цифру.

**Интерфейс этапа.** Каждый этап в `pipeline/`:

```python
class Stage(Protocol):
    name: str
    version: str

    def run(self, ctx: StageContext, inputs: StageInputs) -> StageOutput: ...
```

- этап читает и пишет артефакты только через `ctx.storage`; доступа к БД и вебу у него нет;
- `StageInputs` и `StageOutput` описаны в `contracts/`;
- для каждого этапа есть заглушка, которая возвращает правдоподобный артефакт из `tests/fixtures/`, и в режиме `dev` она явно помечена;
- каждый этап запускается из командной строки: `rapporteur run <этап> <папка конференции>`.

**Воркеры** команды 2 находят этапы через реестр этапов, вызывают их, сохраняют артефакт и ключ кэша (ADR-005) и ничего не знают о том, что этап делает внутри. Порядок этапов и ожидание проверок человека задаёт граф из ADR-009.

**Процесс.**

- [CODEOWNERS](../../CODEOWNERS) закрепляет каталоги за ведущими потоков и автоматически назначает ревьюера из другой команды.
- Изменения `contracts/` и `docs/adr/` требуют одобрения обеих команд. CODEOWNERS только назначает ревьюеров, поэтому требование закрепляется правилом защиты основной ветки.
- Синхронизация раз в неделю на 30 минут; показ рабочего сценария в конце каждой фазы.

## Последствия

- Команда 2 строит интерфейс и воркеры на заглушках, не дожидаясь моделей. Команда 1 отлаживает этапы из командной строки без веба.
- Каждое изменение контракта стоит ревью двух команд; это осознанная цена за отсутствие сюрпризов на интеграции.
- В CI проверяется, что примеры из `contracts/examples/` проходят схемы и что TS-типы сгенерированы из текущей версии.

## Когда пересмотреть

Если состав команд или распределение потоков изменится так, что граница по `pipeline/` перестанет совпадать с границей ответственности.
