# ADR-010. Сервер инференса: vLLM и Ollama

- Статус: Предложено; решение по замерам P0-03 и P1-10
- Дата: 2026-11-01
- Ведёт: К1 · лид, замеры К2 · A
- Связано: spec §2, §8.1, §8.2, §9, ADR-001, ADR-002

## Контекст

ADR-001 закрепил vLLM, ADR-002 строит на нём режимы работы двух A100. Команда 1 предложила запускать модели через Ollama в контейнере с внешней папкой весов: так проще управлять моделями. Образ доступен, в `docker-compose` папка подключается через `volumes`.

Внешняя папка весов не отличает варианты: vLLM читает модель из смонтированного каталога так же, и §2 уже требует держать веса в томе. Разница в другом.

| Требование | vLLM | Ollama |
| --- | --- | --- |
| BF16 без квантизации (§9) | штатно | только если для модели есть BF16 в GGUF; проверить |
| Две карты, NVLink | tensor parallel, TP = 2 | модель, не влезшая на одну карту, распределяется по всем; TP в документации не описан |
| Параллельные запросы | штатная пакетная обработка | `OLLAMA_NUM_PARALLEL`, по умолчанию 1; память растёт как параллельность × контекст |
| JSON Schema | guided decoding | `format` или `response_format`, грамматика llama.cpp |
| Рассуждение вместе со схемой | через reasoning-парсер, проверить в P0-03 | не подтверждено документацией; проверить |
| Смена модели на этапе | sleep и wake, нужен управляющий процесс (ADR-002) | автоматически по имени модели, загрузка заново с диска |
| Управление весами | каталоги с ревизиями, контрольные суммы считаем сами | хранилище с адресацией по digest, `ollama create` из Modelfile |
| Офлайн (§2) | `HF_HUB_OFFLINE=1` | том с моделями, `OLLAMA_NO_CLOUD=1`, исходящий трафик закрыт контейнером |
| OpenAI-совместимый API | да | да, `seed` и `reasoning_effort` поддержаны |

Две оговорки по источникам. Сторонние замеры на A100 показывают многократный отрыв vLLM по пропускной способности при параллельной нагрузке, но цифры в обзорах сильно расходятся и не воспроизводились. Есть сообщение о нестрогом соблюдении JSON Schema для Qwen 3.5 и 3.6 в Ollama (апрель 2026), и эти модели — наш базовый кандидат; первоисточник не проверен. Обе вещи проверяются замером.

На машине разработки команды 1 образ Ollama 0.30.11 есть, моделей нет, карта одна (RTX 3060, 12 ГБ). Модели класса ~27B на ней не проверить.

## Варианты

1. Только vLLM, как в ADR-001.
2. Заменить vLLM на Ollama. Спецификация упрощается, но без замера теряются TP на NVLink и BF16, от которых зависят режимы ADR-002 и обработка 100 докладов за ночь.
3. Оба движка за одним клиентом. Ollama — для локальной разработки на одной карте и кандидат на сервере; прод выбирается замером.

## Решение (предлагаемое)

Вариант 3.

1. Код обращается к модели только через клиент-абстракцию (spec §8.2) по OpenAI-совместимому API. Движок — поле профиля модели (`vllm`, `ollama`), конвейер о нём не знает.
2. Различия движков закрывает адаптер клиента: способ передать схему, рассуждение, управление загрузкой моделей.
3. Локально у команды 1 Ollama поднимается в Docker Compose с внешней папкой весов.
4. В P0-03 к замерам добавляется Ollama на тех же запросах, что и vLLM.
5. До решения ADR-001 действует: `vllm` остаётся сервисом по умолчанию в профилях `gpu` и `prod`.

Критерий для прода: Ollama заменяет vLLM, только если на сервере проходит схему на 100% ответов шага А вместе с рассуждением, держит контекст 32K при нужной параллельности и даёт прогнозируемое время конференции на 100 докладов в пределах ночи. При равном качестве выбирается более простой в эксплуатации вариант.

## Последствия

- Контракт профиля модели хранит движок, поэтому выбор не затрагивает этапы, API и интерфейс.
- Управляющий процесс из ADR-002 нужен только для vLLM.
- При выборе Ollama меняются ADR-001, ADR-002, spec §8.1, §8.3 и §9, а веса поставляются как содержимое каталога моделей Ollama.
- Замеры добавляют К2 · A работы в Ф0.

## Когда пересмотреть

- После P1-10.
- Если Ollama получит документированный tensor parallel или закреплённая версия vLLM не поддержит выбранную модель.
