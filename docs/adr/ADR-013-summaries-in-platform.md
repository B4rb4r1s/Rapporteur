# ADR-013. Сводки и сборка справки через платформу

- Статус: Предложено командой 1; ждёт одобрения командой 2
- Дата: 2026-11-06
- Ведёт: К1 · лид
- Связано: spec §3, §6.7, §7, P1-06…P1-08, P1-11, P1-12, P1-14, ADR-003, ADR-005, ADR-007, ADR-009, ADR-012

## Контекст

Этапы `facts`, `verify` и `summary` и сборка справки работают в CLI конвейера (`make report`),
но не через воркеры. Этапам сводки нужен пакет фрагментов доклада (`TalkFragmentPack`),
а планировщик передаёт этапу доклада выходы `slides` и `notes` его файлов. Кто и где строит пакет,
не решено. В пакете фрагменты ссылаются на файл по `source_file_id`, а этот id назначает БД
(uuid4), и этап его не знает. Таблиц фрагментов, утверждений и сводок нет, задачи сборки справки
тоже нет. Без этого не работают редактор P1-12 и показ P1-13.

## Рассмотренные варианты

Где строится пакет:

1. Этап `facts` строит пакет сам из `slides` и `notes`. Тогда `verify` и `summary` строят его
   заново или пакет приходится вкладывать в `FactsArtifact`.
2. Адаптер backend строит пакет из таблиц перед постановкой `facts`. Ключ задачи тогда зависит
   от состояния БД, а не от входов, и нумерация меток уходит из `pipeline/`.
3. Отдельный этап графа `pack` строит пакет из выходов `slides` и `notes` и публикует его
   артефактом. Этапы сводки получают этот артефакт.

Как этап узнаёт id файла:

1. Новое поле `StageInputs` со списком id файлов — изменение общего входа всех этапов.
2. Карта «SHA → id» в конфигурации этапа: хэш конфигурации меняется при каждой загрузке файла,
   и пересчитываются пакеты и LLM-шаги всех докладов.
3. Детерминированный id: в конференции файл уже уникален по SHA-256
   (`source_files_conference_sha_key`), значит id можно вычислять из пары «конференция, SHA».

## Решение

Варианты 3 и 3.

1. **Этап `pack`.** Область `talk`, ресурс `cpu`, без LLM. Нужны `slides`, `notes`, `asr`
   и `segment`; проверки те же, что у `facts`. Выход — новый артефакт `PackArtifact`
   (`meta` и `pack`). Входы шагов сводки в графе: `facts` ← `pack`; `verify` ← `facts`, `pack`;
   `summary` ← `verify`, `facts`, `pack`. Порядок презентаций в пакете — порядок входов,
   который задаёт планировщик. В Ф1 пакет состоит из слайдов и заметок, стенограммы войдут в Ф2.
2. **Идентификаторы.**
   - `source_file_id = uuid5(conference_id, "file:<sha256>")`, функция
     `rapporteur_contracts.ids.source_file_id`. Backend назначает этот id при приёме файла.
   - `fragment_id = uuid5(source_file_id, "<kind>:<locator>")`. Фрагмент принадлежит файлу,
     а не докладу: перепривязка файла его id не меняет.
   - `revision_id = uuid5(fragment_id, <normalized_text>)`.

   Пакет собирается без обращения к БД, а его id совпадают с записями таблиц.
3. **Запись в БД — backend (К2 · B).** После успешного `pack` backend добавляет фрагменты
   и ревизии из `PackArtifact`, если их ещё нет. После `summary` записывает утверждения
   и сводку из `VerifiedClaimsArtifact` и `SummaryArtifact` и переводит доклад в `processed`.
   Правки человека создают новые версии в БД (ADR-003). В Ф1 текст фрагментов не правится.
   Когда правка появится (стенограммы, Ф2), ревизии человека придут в `pack` отдельным входом.
4. **Профиль модели.** Если в конфигурации этапа нет `profile`, `facts` и `summary` берут
   профиль по умолчанию из `pipeline/profiles.yaml`. Профиль целиком входит в хэш конфигурации,
   поэтому смена профиля перезапускает шаги сводки. Backend может передать другой профиль через
   конфигурацию этапа (P1-10).
5. **Воркеры.** Этап с LLM получает в `StageContext` клиент Ollama по `OLLAMA_URL`.
   В dev `facts` и `summary` — заглушки с `meta.stub=true`, а `pack` и `verify` настоящие:
   модель им не нужна. Образ воркера содержит `prompts/`, `templates/` и `pipeline/profiles.yaml`.
   Пока на установке один профиль, отдельная группировка задач по профилю не нужна:
   воркер и так берёт подряд задачи одного этапа.
6. **Сборка справки** — отдельная задача `report` (область `conference`, ресурс `cpu`), а не узел
   графа: её запускает пользователь. Backend записывает в хранилище запрос `ReportRequest`.
   Запрос содержит конференцию, секции, доклады, персоны, выборку и подтверждение непроверенных
   докладов. Затем backend ставит задачу с этим запросом и `SummaryArtifact` выбранных докладов.
   Этап собирает справку по бланку, публикует файлы (ADR-005) и `ReportArtifact` со снимком
   `ReportInput`. Из артефакта backend создаёт `ReportVersion`. Ошибка выборки, бланка
   или подтверждения — код `report_invalid`.
7. **Ключ кэша этапа доклада включает id доклада** (уточнение ADR-005). Пакет одних и тех же
   слайдов у двух докладов разный: в нём id доклада. Без этого после перепривязки файла пакет
   одного доклада переиспользовался бы для другого. Ключи этапов файлов не меняются, и разбор
   одного файла по-прежнему общий для конференций.

## Последствия

- Пакет кэшируется как любой артефакт: LLM-шаги не перезапускаются, пока не изменились
  слайды, заметки или профиль.
- Backend не дублирует нумерацию меток и не вычисляет id фрагментов: он читает их из артефакта.
- id файлов, загруженных до этого решения, не совпадают с формулой. Такие dev-конференции
  нужно загрузить заново.
- В CLI изменились id фрагментов, поэтому результаты шагов сводки из старого кэша `make report`
  не переиспользуются.
- Правка текста фрагментов человеком потребует нового входа `pack`; формат входа решается в Ф2.
- Старые задачи `summary` остаются в очереди после смены версии этапа или профиля. В запрос
  сборки backend передаёт только текущую сводку доклада: две сводки одного доклада — ошибка.
- Для справки нужны даты конференции (переменная `period` бланка) и докладчики в реестре.
  Без дат сборка отклоняется с `report_invalid`. Без докладчиков бланк опускает скобки
  и число докладчиков.
